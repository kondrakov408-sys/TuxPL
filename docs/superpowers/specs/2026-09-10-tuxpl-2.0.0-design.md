# TuxPL 2.0.0 — Полная финальная спецификация архитектуры

## Введение

TuxPL 2.0.0 — детерминированный эзотерический язык программирования с самомодифицирующейся виртуальной машиной (Self-Modifying VM), единой памятью кода и данных (Unified Memory), динамическим рантайм-декодером, эволюционирующим геномом и детерминированным параллелизмом на двух конкурирующих контекстах исполнения.

---

## 1. Режимы и флаги CLI

Командная строка принимает **строго один основной режим** и произвольное число совместимых модификаторов:

```bash
tuxpl [PRIMARY_MODE] [MODIFIERS] <file.tux>
```

### Основные режимы (Primary Modes, взаимоисключающие):
1. `--CLASSIC` (синоним `--PLS`): Классический стековый калькулятор TuxPL 1.0.0 со старым поведением и математической данью при выходе.
2. `--CURSED` (режим по умолчанию, если режим не указан): Адский режим 1.0.0 (проверка Arch Linux, спячка в выходные дни, имя файла равное числу бит `<bits>.tux`, лицензии из каталога `Tux/`, контрольная буква T/U/X).
3. `--PURGATORY`: Базовый режим самомодификации (Unified Memory, детерминированные мутации после каждого шага, старение инструкций, один контекст `TUX_A`).
4. `--APOCALYPSE`: Полная машина боли:
   * Unified Memory на 65536 ячеек;
   * Двухконтекстная детерминированная модель (`TUX_A` и `TUX_B`);
   * Детерминированный планировщик многозадачности (`scheduler.c`);
   * Динамическое декодирование опкодов на основе `program_key`, `Genome` и `Entropy`;
   * Цепочка динамических ширин инструкций (Dynamic Width Chaining);
   * Связанность регистров (Register Coupling Graph);
   * Семантический долг времени (Time Debt) и Companion-файлы (`.tu`).

### Модификаторы (Modifiers, ортогональные):
* `--REVERSIBLE`: Включение термодинамической проверки обратимости операций.
* `--DISASM`: Честный полиморфный дизассемблер.
* `--TRACE`: Пошаговый вывод трассы выполнения (Step, Context, PC, Opcode, Regs, Debt).
* `--TRACE-STATE`: Полный диагностический дамп состояния (включая хромосомы Genome и пул Entropy).

## 2. Модель Unified Memory и структура `TuxCell`

Память изолирована в песочнице на 65536 ячеек (`TUX_MEM_SIZE = 65536`, диапазон адресов $0 \dots 65535$). Код, данные, переменные и стек физически размещаются в общем пространстве `memory[65536]`.

```c
typedef struct {
    int64_t  val;          /* Каноническое хранилище данных (Canonical Storage Value) */
    uint16_t raw_code;     /* 16-битный state payload (не ограничен 0..41) */
    uint8_t  type_tag;     /* Семантический тип данных: I8..I64, TRIT, ADDR, OPCODE */
    uint8_t  age;          /* Возраст: TUX_AGE_YOUNG, ADULT, OLD, DEAD */
    uint8_t  gen;          /* Поколение инструкции (0..255) */
    uint8_t  flags;        /* Битовые флаги: DORMANT, MUTATED, CLONED, CORRUPTED... */
    uint32_t lineage;      /* Детерминированный идентификатор ветви клонирования */
    uint32_t exec_count;   /* Эволюционный счётчик исполнений (НЕ откатывается при UNDO!) */
} TuxCell;
```

### Правила полей:
* `val` — первичное числовое значение.
* `raw_code` — 16-битный закодированный образ для декодера.
* Если `type_tag == TUX_TYPE_OPCODE`, то `raw_code` является первичным входом для декодера.
* Для остальных `type_tag` первичным входом для декодера является `val`.
* В ячейке памяти **не хранится постоянный декодированный опкод**. Опкод синтезируется «на лету» чистой функцией декодера.
* Для любой ячейки с `age == TUX_AGE_DEAD` декодер **гарантированно возвращает `OP_NOP`**.

## 3. Математика: CRAZY64, Identity, Genome и Entropy

1. **`tux_crazy64(uint64_t a, uint64_t b)`**:
   * Все вычисления выполняются строго по модулю $2^{64}$.
   * Использует два прохода по 20 троичных разрядов матрицы Malbolge (`CRAZY_TRIT[3][3]`) с последующим перекрёстным побитовым перемешиванием.
2. **Program Fingerprint vs Program Key**:
   * `source_hash` вычисляется строго по сырым байтам исходного файла до любой нормализации.
   * `program_key = tux_derive_program_key(&fingerprint)`.
   * `program_key` неизменяем и определяет паспорт программы.
3. **Оверрайды тестирования**:
   * `TUX_ENTROPY_SEED=<uint64>` заменяет начальный сид пула энтропии, не затрагивая `program_key`.
   * `TUX_GENOME=<uint64>` задаёт сид, из которого детерминированно выводятся 4 хромосомы $G_0 \dots G_3$, не меняя `program_key`.
   * `TUX_TIME=<секунды>` детерминированно фиксирует системное время.
4. **Эволюция генома**:
   $$G_{next}[0] = \text{tux\_crazy64}(G[0] \oplus \text{result}, \text{Entropy.pool})$$
   $$G_{next}[1] = \text{tux\_crazy64}(G[1] \oplus G_{next}[0], \text{Registers}[1])$$
   $$G_{next}[2] = \text{tux\_crazy64}(G[2] \oplus \text{PC\_CODE}, G_{next}[1])$$
   $$G_{next}[3] = (G[3] \text{ ROR } 13) \oplus G_{next}[0] \oplus G_{next}[2]$$

## 4. Runtime Decoder и динамическая ширина

1. **Чистый DECODE**:
   $$\text{decoded} = \text{decode}(\text{snapshot})$$
   Декодер не имеет побочных эффектов. При декодировании учитываются `program_key`, `Genome[0]`, `Entropy.pool`, `PC_CODE`, `Registers[0]`, `age` и `gen`.
2. **Динамическая ширина**:
   * Начальная ширина $W_0$ определяется числом $N_U$ при загрузке.
   * На рантайме ширина $W_t \in \{1, 2, 3, 4\}$ синтезируется детерминированно:
     $$W_t = ((\text{tux\_crazy64}(\text{cell.val}, \text{Genome}[1] \oplus W_{t-1}) \gg 16) \& 0x03) + 1$$
   * $W_t$ фиксируется в снимке выборки текущей инструкции и неизменна до конца шага.

## 5. Мутации, клонирование, старение и распад

1. **Точная формула `mutation_encode()`**:
   $$\text{mutation\_encode}(val, \text{key}, G_0) = (\text{uint16\_t})(\text{tux\_crazy64}(val \oplus \text{key}, G_0 \text{ ROR } 17) \ \& \ 0xFFFF)$$
2. **Клонирование (`OP_CLONE`)**:
   * При `src.gen == 255`: поколение насыщается (`dst.gen = 255`) и вызывается `troll_die(TR_AGE)`.
   * Лимит активных исполняемых ячеек в памяти `TUX_MAX_ACTIVE_CODE = 16384`. Превышение лимита $\implies$ `troll_die(TR_MEMRANGE)`.
3. **Dormant Resonance**:
   * Проверка резонанса происходит строго после фазы `GENOME UPDATE` (фаза 6.1).
   * Если $(\text{Genome}[3] \oplus \text{addr}) \pmod{256} == 0$, ячейка просыпается (снимается `TUX_FLAG_DORMANT`).

## 6. Двухконтекстная модель и детерминированный планировщик

1. **Канонический порядок фаз**:
   1. `FETCH` (из `active_ctx.pc_code`)
   2. `DECODE` (чистая функция)
   3. `EXECUTE` (над `active_ctx`)
   4. `MUTATE` (выполненная ячейка)
   5. `REGISTER COUPLING` (внутри `active_ctx.regs`)
   6. `GENOME UPDATE` (общий геном)
   7. `DORMANT RESONANCE` (фоновое пробуждение)
   8. `PC UPDATE` (**только для завершившего шаг `active_ctx`**)
   9. `SCHEDULE` (выбор следующего активного контекста)
2. **Параметры старта**:
   * `TUX_A`: `pc_code = 0`, `pc_data = 1024`.
   * `TUX_B`: `pc_code = (program_key ^ Genome[1]) % TUX_MEM_SIZE`. Сложный для ручного предсказания, но полностью детерминированный старт в любой точке Unified Memory.
   * `pc_data_B = (pc_code_B + 512 + (Genome[2] % 1024)) % TUX_MEM_SIZE`.
3. **Планировщик (`scheduler.c`)**:
   * Читает актуальное состояние памяти на момент фазы 8:
     $$\text{metric} = \text{tux\_crazy64}((V_{\text{pc}} + V_{\text{reg}} + V_{\text{mem}}) \pmod{2^{64}}, \text{sched\_state})$$
     $$\text{next\_ctx\_id} = \text{metric} \pmod{2}$$

---

## 7. Обратимость, Time Debt, Companion и ошибки

1. **`OP_UNDO` vs `--REVERSIBLE`**:
   * `OP_UNDO` всегда восстанавливает **только обратимое состояние данных** (стек, vars, регистры, `PC_DATA`, обратимые модификации `val`).
   * Мутации кода, возраст, поколения, геном, счётчик `exec_count` и `consecutive_pushes` **не откатываются**.
   * В `--REVERSIBLE` режиме рантайм проверяет, сохранён ли дельта-снимок данных перед операцией. Если буфер полон $\implies$ `troll_die(TR_PARADOX)`.
2. **Companion-файл (`.tu`)**:
   * В режиме `--APOCALYPSE` наличие одноимённого файла `<basename>.tu` рядом автоматически активирует companion semantics.
   * Заголовок содержит магические байты `TUX2`, `source_hash`, `genome_seed` и 4 $\times$ 64-битных `register_seeds`.
   * Регистры $R_B[i] = (\text{int64\_t})\text{seeds}[i]$.
   * Отсутствие при наличии требования $\implies$ `troll_die(TR_ORPHAN)`.
   * Несовпадение контрольной суммы $\implies$ `troll_die(TR_HERESY)`.
3. **Расширенные коды ошибок `troll.c`**:
   * `TR_DECODE`, `TR_MUTATION`, `TR_PARADOX`, `TR_GENOME`, `TR_AGE`, `TR_ORPHAN`, `TR_HERESY`, `TR_NO_HISTORY`, `TR_DORMANT`, `TR_EXECUTION`.
